---
applies_to: **/*.json
---

# Do not include comments in .json files
Standard `.json` does not support comments; use `.jsonc` or a documented schema instead of inline comments.

Good:
```json
{ "retries": 3 }
```

Bad:
```json
{ "retries": 3 /* default */ }
```

# Keys should use consistent casing
Object keys within a JSON file should consistently use one casing convention (camelCase or snake_case), not a mix.

Good:
```json
{ "userId": 1, "userName": "ada" }
```

Bad:
```json
{ "userId": 1, "user_name": "ada" }
```

# Avoid trailing commas
Standard JSON does not allow trailing commas after the last element/property; they will fail to parse.

Good:
```json
{ "a": 1, "b": 2 }
```

Bad:
```json
{ "a": 1, "b": 2, }
```

# Do not duplicate keys in the same object
A JSON object must not define the same key twice; the duplicate silently overwrites the earlier value.

Good:
```json
{ "timeout": 1000 }
```

Bad:
```json
{ "timeout": 500, "timeout": 1000 }
```

# Large generated JSON files should not be hand-edited
A file generated by a build/lock process (e.g. a lockfile) should not have manual edits mixed in.

Good:
```json
// regenerate via `npm install`, do not edit package-lock.json by hand
```

Bad:
```json
// package-lock.json with one entry manually tweaked
```

# Avoid deeply nested structures
JSON nested more than about 5 levels deep is hard to review and maintain; consider flattening or splitting.

Good:
```json
{ "user": { "profile": { "address": { "city": "..." } } } }
```

Bad:
```json
{ "a": { "b": { "c": { "d": { "e": { "f": "..." } } } } } }
```

# Do not store secrets in committed JSON config
API keys, passwords, or tokens must not appear as literal values in committed `.json` configuration files.

Good:
```json
{ "apiKey": "${TYPESAFE_API_KEY}" }
```

Bad:
```json
{ "apiKey": "sk_live_51Hxyz..." }
```

# Arrays of objects should have a consistent shape
Each object within a JSON array should share the same set of keys unless the schema explicitly allows variation.

Good:
```json
[{ "id": 1, "name": "a" }, { "id": 2, "name": "b" }]
```

Bad:
```json
[{ "id": 1, "name": "a" }, { "id": 2 }]
```

# Avoid null when an absent key would be clearer
Prefer omitting an optional key over including it with a `null` value, unless the consumer specifically distinguishes 'absent' from 'null'.

Good:
```json
{ "nickname": "Ada" }
```

Bad:
```json
{ "nickname": null }
```

# Do not use JSON5-only syntax in strict .json files
Unquoted keys, comments, or trailing commas are not valid standard JSON; keep `.json` files strictly conformant.

Good:
```json
{ "name": "app" }
```

Bad:
```json
{ name: 'app', }
```

# Version fields should follow semantic versioning
A `version` field should be a valid semver string (e.g. `1.4.0`), not an arbitrary label.

Good:
```json
{ "version": "1.4.0" }
```

Bad:
```json
{ "version": "v1_final" }
```

# Do not commit machine-specific absolute paths
JSON configuration must not contain absolute filesystem paths specific to one developer's machine.

Good:
```json
{ "outDir": "./dist" }
```

Bad:
```json
{ "outDir": "/Users/ada/project/dist" }
```

# Boolean flags should have unambiguous names
A boolean config key's name should make its true/false meaning obvious without reading documentation.

Good:
```json
{ "isEnabled": true }
```

Bad:
```json
{ "flag": true }
```

# Format large hand-maintained JSON for readability
A JSON file that humans edit directly should be pretty-printed, not minified onto one line.

Good:
```json
{
  "name": "app",
  "version": "1.0.0"
}
```

Bad:
```json
{"name":"app","version":"1.0.0","dependencies":{"a":"1.0.0","b":"2.0.0"}}
```

# Do not leave placeholder values in committed config
Values like `"TODO"` or `"CHANGEME"` must be replaced with real values before committing.

Good:
```json
{ "apiUrl": "https://api.example.com" }
```

Bad:
```json
{ "apiUrl": "CHANGEME" }
```
